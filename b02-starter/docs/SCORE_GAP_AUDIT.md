# 本地 79 分与官网 75.24：只读核对报告

日期：2026-11-16。核对对象是已提交的 v1.1，官网 75.24 按用户反馈记录。未训练、未调阈值、未改已提交代码／结果，也没有重新上传。结论和数值证据见 [机器记录](score-gap-audit-20261116.json)。

## 最重要的发现：同名文件不是同一份输入

此前仅凭 `train_001` 至 `train_005` 的相同文件名，推断训练 CSV 与官方 DAT 是同一批场景，依据不足。现撤回这个直接映射判断。

官方 TCP 的实际输入计数，与当前训练 ZIP 的同名 CSV 行数，五份全部不一致：

| 文件编号 | 训练 CSV 点数 | 官方 DAT/TCP 点数 | 同名 CSV 冻结模型输出 | 已提交官方输出 |
| --- | ---: | ---: | ---: | ---: |
| train_001 | 136,425 | 219,111 | 23,743 | 18,913 |
| train_002 | 207,360 | 170,826 | 20,069 | 14,857 |
| train_003 | 83,620 | 177,088 | 15,587 | 23,541 |
| train_004 | 184,986 | 180,209 | 17,778 | 21,375 |
| train_005 | 120,061 | 161,402 | 19,889 | 19,332 |

训练 CSV 合计 732452 点，官方 DAT 合计 908636 点；train_001 第一圈分别为 144 点与 58 点。第一圈和全场景点数都不同，不能用前置空圈、float32 舍入、忽略几个 -1 点等解释为同一条输入序列。

这不证明底层模拟场景或目标轨迹完全没有重合，可能是不同场景、重新编号或不同点迹版本；**没有主办方映射和真实标签之前，不能把同名 CSV 的 Batch_ID 用于给 A 榜结果打分，也不能断言 A 榜用了哪几个训练／封存场景。**

为排除“拿错训练版本”这一额外疑问，还核对了历史 v1 训练／开发用的 70 文件子集 ZIP：其 SHA-256 为 `a2bbf6cee329365960a589901b155958a1cdaa7c2f0a09d063a57add4adc4271`；当前原始 200 文件 ZIP 为 `9df7698ae1dcdb155d836ea7f27eaaa95ba0ae20d85c4edce0574f1bea5a5c3b`。ZIP 哈希不同是子集重打包；70 份共享 CSV 逐字节相同，且该检查未打开任何历史 holdout CSV。没有发现这些共享训练／开发文件发生版本替换。

## 最新规则逐项核对

依据用户提供的 11.15 更新 PDF：第 8 页权重，第 9 页掌握率和虚警，第 10 页零碎度和及时性，第 11 页连续跟踪。原页已渲染目视核对，文件 SHA-256 为 `2ef8a9603f0544be83a4727aad26049bffc18a0d241e6e3c8d885e1cba7d9970`。

| 项目 | 规则要点 | 现有本地实现 | 结论 |
| --- | --- | --- | --- |
| 权重 | 0.3／0.1／0.2／0.2／0.2 | 一致 | 未发现权重写错 |
| 掌握率 | 每条真值的匹配点比例，再对真值航迹平均 | 使用逐航迹平均，不使用全部点的总命中率作 30% 子分 | 与公开公式结构一致 |
| 虚警 | 未匹配输出点／真值总点数，1−比值，下限 0 | 对已知 0 标签输出计虚警；训练标签 -1 输出单列忽略 | 分母和公式一致；训练未知标签与官方真实标签无法直接映射 |
| 零碎度 | 仅考察掌握成功真值，按匹配输出航迹数取倒数平均 | 任何至少一个命中点即暂视成功，每个命中过的输出 ID 均参与 | 成功条件和轨迹级匹配阈值未获官方实现确认 |
| 及时性 | 数据时间上的起批时延，MT 是最早匹配输出航迹的开始时间 | 首次匹配点所在圈，减真值首圈加两圈；5 秒/圈 | 存在近似：ID 的更早杂波起点、真实毫秒时间、第三点与第三圈需区分 |
| 连续跟踪 | 同一输出 ID 的最大匹配总点数，分母不统计真值前两点，min 上限 1 | 同 ID 跨漏圈累计、分母减 2、min 上限 1 | 已采用 min，未沿用旧文档 max；前两点对分子的处理仍可向官方确认 |

“最大连续跟踪”目前不是按无漏点的最长连续段重新计分：文档使用匹配总点数，且用户此前转述同一个 ID 按一条处理；不能擅自改成最长连续无缺口段来凑官网分。

起批及时性用雷达数据时间，不是把程序运行 474 ms 直接当作起批延迟；实际运行过慢导致漏圈／超时是另外一条影响路径。

## 近似项能造成多大影响：仅作敏感性检查

以下均是**同名训练 CSV 的数学诊断**，不是官方 A 榜五项得分，也不是反向搜索参数拟合 75.24：

- 将全部已输出 -1 点按虚警处理：同名五 CSV 的总分下降约 0.361；在原 30 开发文件均值统计上，约下降 0.406。这个特定近似本身不能解释四分差。
- 五个训练 CSV 分数简单平均为 79.910647，当前合并真值统计为 80.016917，相差约 0.106。官方是按场景平均还是跨场景合并仍需确认；不要将此诊断量直接扣在官网分数上。
- 直接按毫秒首匹配时间算及时性，相比圈号近似约降低 0.005 总分；改用输出 ID 的更早起点则约提高 0.297；第三个真实观测点结合 ID 起点约提高 0.496。多数此类修正会使本地更高，因此不能一概拿来解释“本地高、官网低”。
- 连续子分分子也排除真值前两个观测的已命中点：只下降约 0.0033 总分。本次 569 条训练真值航迹中，没有少于等于两点的航迹，也没有不足三次匹配的真值；这些边界不是此诊断集里的四分主因。
- 同名训练诊断中有 387 个输出 ID 命中过多个真值 ID。本地逐点归属能统计到这些点，但官方如果采用更严格的轨迹归属／成功匹配规则，可能给出不同结果。这个统计不能证明官方采用何种规则，也不能直接换算成应扣分数。

## 接口与交付核对

已核对最新版 README、protocol.md、原版 client.py、serve.py 和实际记录：

1. 每包重新初始化状态，五包完整处理；3596 圈、98018 个输出点，两次轨迹字节一致。
2. 原版编码器检查 Time／CircleID／PntID／坐标来自本圈原始点，BatchID 为正 uint32；小端、32 字节点迹和 28 字节航迹的字段顺序与说明一致。
3. 最长官方单圈往返 474 ms，低于 30 秒期限；服务端成功检查所有圈与输出，未见丢包或超时证据。
4. 实际推理种子 20261112、8000 步、起始 0.525、维持 0.05；权重哈希、manifest、代码与结果 ZIP 均未改变，没有加载原基线或另一份权重的证据。
5. 官网结果 ZIP 确实只有五个航迹 DAT，未混入输入 DAT、计时文件、日志或额外目录。

重复结果和字段检查说明交付稳定，但不等于证明本地计分等同官方。当前证据不支持将四分首先归因于显卡、CPU 封装、min/max 未修正或超时漏圈。

## 可确认与仍未知

**已确认：评估数据与统计范围不一致，文件同名也不能对齐；若干本地计分细节仍是已声明的近似。无法确认：这 4.216 分中多少来自数据分布、多少来自官方匹配和计分实现。** 缺少真实 A 榜标签和分项，不能从总分唯一还原官方评测代码，也不能据此认定 v1 框架上限。

对主办方最有价值的询问是：① DAT 和同名训练 CSV 是否重编号／不同版本，是否有可公开的场景映射；② “掌握成功”和输出 ID 与真值轨迹的匹配标准；③ 五包如何汇总、MT 起点如何取，以及能否提供本次五项分数。无需要求公布隐含测试真值，也不为探口径反复消耗提交次数。

公开网页也检查了官网首页，但动态 B02 详情未能通过网页工具读取，本次不宣称取得了更新的评分脚本；规则判断以上述本地 11.15 原件为准。
